# Add historical upstream cost to admin user list

## Goal

在管理员用户管理列表中单独展示每个用户的累计渠道实际成本，让管理员能把用户侧消耗额度与渠道侧成本区分开。

## Background

- 用户列表目前展示 `used_quota`，它代表用户被扣除的额度，并不等同于渠道成本。
- 消费日志已保存用户 ID、计费基础额度 `base_quota`、请求发生时的渠道成本倍率快照 `channel_cost_ratio`，并用 `channel_cost_ratio_estimated` 标记事后推断值。
- 用户明确要求：成本必须仅按每个请求发生时实际渠道的成本倍率快照计算；当前倍率、渠道增删和改名均不得改变历史成本。
- 当前全局/渠道成本统计按消费日志中的成本倍率快照计算，不依赖渠道当前配置；渠道改名或删除不会重算日志历史。
- 用户列表支持分页和搜索，用户管理路由由管理员认证保护。
- HK 当前运行的渠道可用性看板与用户列表使用同一共享 PostgreSQL 日志库；看板的 `CostQuota` 聚合逻辑可以按 `user_id` 扩展，而不需要依赖渠道表。
- HK 现场审计（2026-10-17）：共有 162,851 条消费日志，其中 160,658 条有请求时观测的倍率快照且有基础成本额度，16 条只有回填的 estimated 倍率，2,177 条额度/基础成本均为零；20,005 条日志属于已删除渠道，其中 19,989 条仍有观测倍率快照；至少 10 个渠道 ID 的历史日志出现过多个观测倍率。历史渠道删除、改名和倍率变化因此都能由日志快照正确保留。
- 看板的历史成本聚合不是“不可用”的数据：当前 HK 审计按用户 ID 聚合得到 12 个有消费记录的用户，且所有用户都有可观测快照成本记录；看板的总成本口径可复用其按倍率分桶、从日志直接计算的方式。

## Requirements

- R1：管理员用户列表新增独立的“成本”展示，不替代或重命名现有额度、已用额度展示；成本统计范围为该用户所有消费日志中可按请求时快照验证的累计值。
- R2：每条消费日志的成本按请求日志保存的 `base_quota` 与该请求实际使用的渠道成本倍率快照计算。聚合按日志的 `user_id` 归属，不从当前用户名、渠道名称、渠道 ID 列表或当前渠道配置推算历史数据。
- R3：成本只累计具有请求时真实成本倍率快照且基础成本额度可还原的消费日志。不得把依据当前渠道配置回填并标记为 estimated 的历史倍率当成精确成本；缺少计算依据的记录不通过当前配置补算。
- R4：保持成本为管理员专用字段；不改变用户额度扣费、现有额度展示或普通用户接口。
- R5：列表页和搜索页都要返回对应用户成本，统计应按当前页用户批量聚合，避免每个用户单独查询日志。
- R6：复用渠道可用性看板的日志成本语义和安全额度换算，不再另造一套按当前渠道配置计算的历史成本逻辑；新增用户维度仅改变聚合分组和返回 DTO。

## Acceptance Criteria

- [x] AC1：管理员用户列表有独立的累计“成本”数值，与已用额度并列且区分清楚。
- [x] AC2：列表及搜索结果的成本按用户 ID 汇总消费日志，并且不对每个用户发起单独的日志查询；聚合结果与看板同口径。
- [x] AC3：同一历史请求的成本保持基于日志内请求时的 `base_quota` 和 `channel_cost_ratio`；改变、重命名、删除或新增渠道不会改变已发生请求的成本汇总。
- [x] AC4：缺少真实请求时倍率快照或基础额度的日志不会被当前渠道倍率伪装成精确成本；如存在被排除记录，响应和界面可识别该用户成本统计不完整。看板现有 estimated 回退值不能被用户成本列冒充为精确值。
- [x] AC5：现有额度/已用额度字段与用户计费行为不变，成本字段只通过管理员用户列表返回。
- [x] AC6：后端有确定性回归测试覆盖分页/搜索用户成本归属、倍率快照历史稳定性和无快照旧日志；前端新增成本列的文本经 i18n 支持。
